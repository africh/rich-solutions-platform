## 1. Goal

Ship the package's Agentforce actions. An org's Agentforce agent can call them to answer questions from the synced knowledge graph. When nothing matches, the agent gets an **explicit no-answer result**, never invented content.

The actions are thin adapters over the SB-9 core. That is the same pattern as the REST resources (SB-9) and the global Apex API (SB-10), so all three channels give the same answer (C-application 5.2 rule 2).

The package makes no model call (AP-3, IF-9). The action returns grounding passages with citations, and the org's own Agentforce model writes the reply.

Out of scope:

- Client agents, topics, prompts and instructions. These are extension work (C-application section 7). This repository ships only a generic, unpackaged sample (section 6).
- Import operations. They are not in the tool manifest (SB-7 4.1).
- Semantic or vector retrieval (ADR-001 consequences).
- Per-note access (REQ-15, Needs Alex).

## 4. Action inputs and outputs (`KnowledgeActionIO`)

Invocable variables can only be primitives, lists of primitives, or Apex-defined types whose fields are `@InvocableVariable`. They cannot be maps or arbitrary JSON. So the action types are a flattened mirror of the contract. They add no information the contract lacks (C-application 5.2 rule 1), and the mapping is fixed in this section.

Every class and field is `global`, so that subscriber agents and flows can see them across the namespace (E1 confirms this, section 8). Every `@InvocableVariable` has a `label` and a `description`. **Descriptions of contract fields are copied from the matching `tool-manifest.json` / OpenAPI descriptions**, because an agent chooses actions and fills inputs from these descriptions, and runtime-neutral text keeps all runtimes on one wording. The **action-only fields** have no manifest text; they take their descriptions from the table in 4.3. Test 9.1-7 checks both.

### 4.1 Requests

| Class | Fields (all optional except where marked; null means "not supplied", per the SB-9 6.6 null rule) |
|---|---|
| `ContextRequest` | `question` (String, **required**); `maxNodes` (Integer); `maxChars` (Integer) |
| `SearchRequest` | `query` (String, **required**); `tags` (List<String>); `maxItems` (Integer, contract `limit`); `cursor` (String) |
| `GetNodeRequest` | `nodeId` (String, **required**); `includeBody` (Boolean) |
| `NeighborsRequest` | `nodeId` (String, **required**); `direction` (String); `edgeTypes` (List<String>, contract `types`); `depth` (Integer); `maxItems` (Integer, contract `limit`) |

`@InvocableVariable(required=true)` is set on the required fields, so Agentforce and Flow prompt for them. The SB-9 validator still checks them, because Apex callers can bypass the flag.

### 4.2 Results

Every result type starts with the same five **outcome fields**:

| Field | Type | Meaning |
|---|---|---|
| `outcome` | String | `OK`, `NO_ANSWER` (getContext only, 5.3) or `ERROR` |
| `errorCode` | String | SB-7 4.3 code when `outcome = ERROR`, otherwise null |
| `errorMessage` | String | The envelope `message` when `outcome = ERROR` |
| `errorRetryable` | Boolean | The envelope `retryable` when `outcome = ERROR`, otherwise null. Lets an agent or flow decide to retry without parsing `errorJson` |
| `errorJson` | String | The full SB-7 error envelope as JSON when `outcome = ERROR` (SB-7 4.3: agent tools return the envelope as the tool result) |

Then the operation fields:

| Class | Operation fields |
|---|---|
| `ContextResult` | `question` (String, the contract `question` as the core returns it); `groundingText` (String, section 5.2); `passages` (List<`Passage`>); `truncated` (Boolean); `bundleId`, `bundleCommit` (String) |
| `SearchResult` | `items` (List<`NodeItem`>); `nextCursor` (String); `bundleId`, `bundleCommit` |
| `NodeResult` | `node` (`NodeItem`), with `body` set; `frontmatterJson` (String, the contract `frontmatter` object as JSON); `bundleId`, `bundleCommit` |
| `NeighborsResult` | `node` (`NodeItem`); `edges` (List<`EdgeItem`>); `truncated` |
| `Passage` | `nodeId`, `title`, `path`, `text`, `citation` |
| `NodeItem` | `id`, `title`, `path`, `kind`, `snippet`, `body` (String); `tags` (List<String>); `score` (Decimal) |
| `EdgeItem` | `source`, `target`, `targetText`, `edgeType`, `relation`, `anchor` (String); `resolved` (Boolean); `node` (`NodeItem`, null when unresolved) |

**Mapping notes:**

- `bundle: {id, commit}` is flattened to `bundleId` and `bundleCommit`. Both are null when no bundle has been committed (SB-9 4.2).
- `frontmatter` is an open object, so it is passed as a JSON string. An invocable variable cannot be a map.
- The renames are the SB-9 section 4 renames (`maxItems`, `edgeType`, `edgeTypes`). `commit` becomes `bundleCommit`.
- `NeighborEdge {edge, node}` is flattened into `EdgeItem`, which has the edge fields plus `node`.
- `errorCode`, `errorMessage` and `errorRetryable` are copies of the envelope fields in `errorJson`, kept consistent by `KnowledgeActionSupport`. Test 9.2 checks that they match the envelope.
- `KnowledgeActionSupport` does the mapping, both ways, in one place. Test 9.2 proves that it loses nothing, by converting back to the Contract DTOs and comparing with `KnowledgeApi`. The only fields that do not convert back are the action-only fields in 4.3, which are derived from the contract result.

### 4.3 Descriptions of action-only fields

These fields have no `tool-manifest.json` text. Their `@InvocableVariable` descriptions are exactly these strings, and test 9.1-7 checks them against this table:

| Field | Description |
|---|---|
| `outcome` | `OK` when the call succeeded, `NO_ANSWER` when the knowledge base has no content for the question, `ERROR` when the call failed. |
| `errorCode` | Error code when outcome is ERROR, for example INVALID_REQUEST, NODE_NOT_FOUND, FORBIDDEN, RATE_LIMITED or INTERNAL. |
| `errorMessage` | Human-readable error message when outcome is ERROR. |
| `errorRetryable` | True when the same request may succeed if sent again later. Set only when outcome is ERROR. |
| `errorJson` | The full error envelope as JSON when outcome is ERROR. |
| `groundingText` | The matching passages as numbered text, each with its source citation. Answer only from this text. |
| `bundleId` | Id of the knowledge bundle the result was read from; empty when no bundle has been loaded. |
| `bundleCommit` | Git commit of the knowledge bundle the result was read from; empty when no bundle has been loaded. |
| `frontmatterJson` | The note's frontmatter properties as a JSON object. |

## 5. Behaviour

### 5.1 Common rules (every action)

1. **One class per operation.** Each class has exactly one `global static` `@InvocableMethod` (the platform allows one per class). The method takes `List<Request>` and returns `List<Result>` in the same order. Its `label`, `description` and `category = 'Knowledge'` come from the tool manifest.
2. **Per item:** map the request to the Contract DTO, call `KnowledgeServiceResolver.get().<operation>(dto)`, then map the result. Validation, the permission check, the bundle-consistent read and the extension hook all happen in the core, exactly as for REST and Apex. The hook therefore applies to agents too, which matters if a client hook redacts content.
3. **Errors are results, not exceptions.**
   - A `KnowledgeException` becomes `outcome = ERROR` with the code, message and envelope JSON of that exception.
   - Any other catchable exception becomes `INTERNAL` (generic message, request id, `retryable: true`, SB-9 6.8), like `KnowledgeApi`.
   - The action never throws for a knowledge error. A thrown exception fails the agent turn or the flow, and the agent cannot explain it. An error result lets the agent say that the knowledge service is unavailable or the input was wrong.
   - Governor-limit errors cannot be caught (SB-10 4 rule 4). Rule 4 below keeps each item inside the remaining budget so that they do not occur.
4. **Governor budget (QA M1).** All items of one invocation share one transaction with whatever else the flow or agent turn has already run. A limit failure there cannot be caught and fails the whole transaction, so the action checks the remaining budget **before each item** and defers an item it cannot afford rather than starting it:
   - **Static cap.** At most **10 items** are processed per invocation. This is an upper bound only; the budget check below is what keeps the transaction safe.
   - **Budget check.** Before an item, `KnowledgeActionSupport.canAfford(operation)` compares the remaining limits with the per-call worst case from SB-9 section 8:

     | Limit | Remaining must be at least | Source |
     |---|---|---|
     | SOSL (`Limits.getLimitSoslQueries() - Limits.getSoslQueries()`) | 2 for `getContext` and `searchNodes`; 0 for the others | SB-9 8 |
     | SOQL (`Limits.getLimitQueries() - Limits.getQueries()`) | 7 | SB-9 8 (worst case, any operation) |
     | CPU (`Limits.getLimitCpuTime() - Limits.getCpuTime()`) | 5,000 ms for `getContext`; 2,000 ms for the others | SB-9 test 18 bound; others have no long text scoring |
     | Heap (`Limits.getLimitHeapSize() - Limits.getHeapSize()`) | 1.5 MB | SB-9 8: one `getContext` holds up to 10 texts plus the result |

     The reserves are named constants in `KnowledgeActionSupport`. If SB-9 changes its section 8 costs, the Technical Architect updates this table.
   - **Deferred items.** The first item that is over the static cap or fails the budget check, and every item after it, is not started. Each gets `outcome = ERROR`, `errorCode = RATE_LIMITED`, `errorRetryable = true`, `details: [{path: "", rule: "budget.<limit>"}]` where `<limit>` is `batch`, `sosl`, `soql`, `cpu` or `heap`. Items already processed keep their results. Stopping at the first deferral keeps the outcome simple to explain: a contiguous tail of the list is deferred.
   - **Why `RATE_LIMITED`.** A deferred item is valid input that would succeed if sent again in a new transaction, so it must be retryable (SB-7 4.3: `RATE_LIMITED`, `retryable: true`). `INVALID_REQUEST` would be wrong, because it is not retryable. The actions are therefore the **one place the base package sends `RATE_LIMITED`**. This amends the SB-9 6.8 line "`RATE_LIMITED` is never sent by the base package" (open point 4).
   - **Callers.** Agents send one request per call and do not normally hit the budget. The guide (section 7) tells flow builders that bulk flows, in particular **record-triggered flows, which the platform can batch up to 200 records into one action call, must call these actions from an asynchronous path** (the flow's "Run Asynchronously" path, or a scheduled path), and that deferred items should be retried in a new transaction, for example by a later scheduled path.
5. **Independence.** Each item is processed on its own. One item's error does not affect the others.
6. **Trigger context (QA m3).** If SB-10 E1 confirms that SOSL is not allowed in triggers, the context and search actions apply the same `context.trigger` guard as `KnowledgeApi`. Record-triggered flows run in the trigger transaction, so that guard may apply to them. Two facts are not yet shown, and E1 (section 8) records both: whether `Trigger.isExecuting` is true in Apex invoked from a record-triggered flow, and whether the SOSL restriction applies there.
   - If both hold, the guard keys on `Trigger.isExecuting` as in `KnowledgeApi`, and the `context.trigger` rule applies to actions as well as Apex. SB-10 4 rule 5 says "agent calls never run in a trigger"; that stays true for agents, and the SB-9 6.6 rule table records that flows can (open point 4).
   - If SOSL is restricted but `Trigger.isExecuting` is false there, the Developer records it and stops on this rule; the Technical Architect revises it. Nothing is guessed.
   - If SOSL works there, no guard is added.
   - Either way, the guide says to use an asynchronous path for these actions in record-triggered flows (rule 4).

### 5.2 `Answer from Knowledge` (`KnowledgeGetContextAction`, primary)

This is the action the sample topic tells the agent to use for questions (section 6). It calls `getContext` and adds one presentation field, **`groundingText`**, because agents read text more reliably than nested lists:

```
[1] <title> (source: <citation>)
<passage text>

[2] ...
```

- Passages appear in result order. They are separated by one blank line. Nothing is added except the header line per passage.
- `groundingText` is derived only from `passages`, so it adds no information the contract lacks. The structured `passages` list is returned as well, for flows and custom agents.
- The length of `groundingText` is the total passage text (at most `maxChars`, SB-9 6.5) plus about 100 characters of header per passage. Experiment E2 (section 8) measures how much action output an agent accepts. If that limit is lower than the contract default `maxChars` (20,000), the sample agent action sets a lower `maxChars` input (section 6). The contract default does not change.

### 5.3 The explicit no-answer result (REQ-4 AC 2)

If `getContext` returns an empty `passages` list (SB-9 6.5 step 7: no chosen node has a keyword hit, or the question has no keywords, or there is no committed bundle), the action returns:

- `outcome = NO_ANSWER`
- `passages = []`, `truncated = false`
- `groundingText` = the fixed sentence `NO_ANSWER: The knowledge base has no content that matches this question.`
- The bundle fields as returned (null if there is no bundle)

The fixed sentence is a constant in `KnowledgeActionSupport`. It is the same in every org and is never generated. The sample topic instructions (section 6) tell the agent: if the outcome is `NO_ANSWER`, say that the knowledge base does not cover the question, and do not answer from general knowledge.

Errors are different: an `ERROR` outcome means the agent could not check (section 5.1 rule 3). The sample instructions say so, and the guide explains both outcomes.

The other three actions never return `NO_ANSWER`. An empty search is `OK` with no items, and a missing node is `ERROR` / `NODE_NOT_FOUND`, as on the other channels.

### 5.4 Access

- The agent runs the action as its **running user**. For an employee agent, that is the signed-in user. For a service agent, it is the agent user configured in Setup. That user needs `Knowledge_Reader`, or every action returns `ERROR` / `FORBIDDEN`. The guide and the sample README say this first.
- 11a adds Apex class access to the four action classes in `Knowledge_Reader`. The `Knowledge_Read` custom permission in the core is the real gate (SB-9 6.7).
- The guest check in the core (SB-9 6.7) also blocks an unauthenticated site or portal agent user. Exposing knowledge to guests is out of scope for the MVP.

## 9. Test approach

### 9.1 Apex unit tests (11a)

These run with `RunLocalTests` in a development scratch org, using SB-9's `KnowledgeTestData` with synthetic "Example Corp" content and `Test.setFixedSearchResults`. Coverage on the action classes and `KnowledgeActionSupport` is at least 95 %.

| # | Test | Proves |
|---|---|---|
| 1 | "Answer from Knowledge" with a covered question | `outcome = OK`; passages equal `KnowledgeApi.getContext` for the same input; `groundingText` format (5.2); citations `<path>@<commit>` |
| 2 | An uncovered question; a question with only stop words; no committed bundle | `outcome = NO_ANSWER`, the fixed sentence, empty passages, `truncated = false` (REQ-4 AC 2) |
| 3 | Each action with valid input | `outcome = OK`; every mapped field is set (section 4) |
| 4 | Each action with an invalid field, a null required field, and null optional fields | `ERROR` / `INVALID_REQUEST` with the validator's `details` in `errorJson`; optional nulls give the defaults (SB-9 6.6) |
| 5 | A user without `Knowledge_Reader` (`System.runAs`) | `ERROR` / `FORBIDDEN` from all four actions, no content |
| 6 | A stub service that throws a `NullPointerException`, via `KnowledgeServiceResolver.overrideForTest` (SB-9 5.2) | `ERROR` / `INTERNAL`, `retryable: true`, nothing thrown to the caller, no stack trace |
| 7 | Descriptions: every `@InvocableMethod` and contract-field `@InvocableVariable` description against the tool-manifest text (copied into the test as a string, with a comment naming the source file); every action-only field against the 4.3 table | Agents see the runtime-neutral wording; no field is left without a description |
| 8a | Static cap: 12 valid requests, plus a run with 12 requests where item 3 is invalid | Items 1 to 10 processed in order (item 3 `ERROR` / `INVALID_REQUEST`, the others `OK`); items 11 and 12 `ERROR` / `RATE_LIMITED`, `errorRetryable = true`, rule `budget.batch` |
| 8b | SOSL budget: the test runs 18 SOSL queries first, then sends 3 "Answer from Knowledge" requests | Item 1 `OK`; items 2 and 3 `RATE_LIMITED`, rule `budget.sosl`; no `System.LimitException`; `Limits.getSoslQueries() = 20` at the end |
| 8c | SOQL, CPU and heap budget, via a `@TestVisible` remaining-budget seam in `KnowledgeActionSupport` that stands in for each `Limits` reading | Below each reserve the next item and all later items are `RATE_LIMITED` with rule `budget.soql`, `budget.cpu` or `budget.heap`; earlier results unchanged |
| 8d | Resend: each deferred item from 8a, sent alone in a new test transaction | `OK`, same result as an undeferred call (deferral is retryable, not a rejection) |
| 9 | Hook configured (SB-9 test-seam records) that redacts a passage | The redaction is visible in the action output, so agents get the hooked result |

### 9.2 Parity test (`KnowledgeActionParityTest`, 11a)

This is the same approach as SB-10 7.2, with the actions compared against `KnowledgeApi`. For each operation it runs a table of inputs: a normal case, a boundary value, an empty result, each error code, a null optional field, and the hook. For each input:

1. Call the action. Convert its result back to the Contract DTOs with `KnowledgeActionSupport`, or its `errorJson` back to an envelope. On `ERROR`, also assert that `errorCode`, `errorMessage` and `errorRetryable` equal the envelope's `code`, `message` and `retryable`.
2. Call `KnowledgeApi.<operation>` with the same input and serialise the result, or the exception's envelope, with `KnowledgeRestSupport`.
3. Assert that both are deep-equal as parsed JSON.

For `getContext`, an `OK` or `NO_ANSWER` action outcome must match the same `ContextResult`, including `question`. `NO_ANSWER` must occur exactly when `passages` is empty. Budget deferral (`RATE_LIMITED`) is action-only and excluded from parity; tests 8a to 8d cover it.

### 9.3 Agent test (11b, Agentforce scratch org)

This is the REQ-4 AC 1 check: an agent with the actions assigned answers a covered question from knowledge-graph content.

1. Create a scratch org from `project-scratch-def.agentforce.json`. Install the package, sync the `basic/` fixture (SB-8 `e2e-sync.sh` steps 1 and 2), and wait 2 minutes for the search index.
2. Deploy the sample with `post-install.sh --agentforce`. Create or choose a test agent, assign the "Knowledge Q&A" topic, and give its running user `Knowledge_Reader`. The sample README lists these steps.
3. Run the agent test definition with the Salesforce CLI agent testing commands (`sf agent test run`). It has three cases:
   - (a) A question the `basic/` fixture covers. Expected: the topic is selected, "Answer from Knowledge" is invoked, and the reply contains the fixture's distinctive phrase and its citation path.
