## 1. Goal

Give subscriber-org Apex one documented `global` method for each MVP read operation. For the same input and the same committed bundle, each method returns the same result as the equivalent REST call, and it throws the same error code (C-application 5.2 rule 2). The API is a thin adapter: all logic stays in SB-9's core.

Out of scope:

- The import operations. They are admin-only and REST-only (C-application 5.2 rule 3).
- Agentforce actions (SB-11).
- A `System.Callable` entry point (section 9, open point 2).
- Per-note access (REQ-15, Needs Alex).

## 4. `KnowledgeApi`

```apex
global with sharing class KnowledgeApi {
    global static KnowledgeResults.NodeResult getNode(KnowledgeRequests.GetNodeRequest request) { ... }
    global static KnowledgeResults.SearchResult searchNodes(KnowledgeRequests.SearchRequest request) { ... }
    global static KnowledgeResults.NeighborResult getNeighbors(KnowledgeRequests.NeighborsRequest request) { ... }
    global static KnowledgeResults.ContextResult getContext(KnowledgeRequests.ContextRequest request) { ... }
}
```

**Rules**

1. **One method per operation, named after the `operationId`.** No overloads and no convenience variants. Every `global` signature stays forever once a version is released (ip-boundary 3.1 rule 4), so the surface is kept to what the contract defines. A later contract minor version adds request fields, not new overloads.
2. **The body is always the same three steps:** null check, `KnowledgeServiceResolver.get().<operation>(request)`, return. A `null` request throws `KnowledgeException` `INVALID_REQUEST` with `details: [{path: "", rule: "required"}]`.
3. **Errors:** the method lets `KnowledgeException` from the core pass through unchanged. Code, message, details and retryable are identical to what the REST resource writes for the same input. Any other catchable exception is wrapped as `KnowledgeException.internal()`, exactly as `KnowledgeRestSupport` does (SB-9 7.3). That is REQ-3's "documented, catchable exception": subscriber code writes `catch (<ns>.KnowledgeException e)` and reads `e.getCode()`, `e.getDetails()` and `e.isRetryable()`.
4. **Governor limits are not catchable** (`System.LimitException`). `docs/apex-api.md` lists the per-call cost from SB-9 section 8: at most 7 SOQL queries, 2 SOSL queries and about 6 MB of heap in the worst case. Callers that make several calls in one transaction must budget for that. The API cannot turn limit errors into `KnowledgeException`, and the guide says so.
5. **Trigger context (experiment E1, section 8).** Apex does not allow SOSL in triggers, and `searchNodes` and `getContext` use SOSL (SB-9 6.3, 6.5).
   - If E1 confirms the restriction: when `Trigger.isExecuting` is true, these two methods throw `INVALID_REQUEST` with `details: [{path: "", rule: "context.trigger"}]` before any query runs. The guide says to call them from a Queueable instead. `getNode` and `getNeighbors` work in triggers.
   - If E1 shows SOSL works in triggers, the guard is left out and the guide says nothing about it.
6. **Results are new objects per call.** A caller may change them freely. The core never keeps or reuses a returned DTO, and it never changes the caller's request object.
7. **`with sharing`** is declared for clarity only. Access is enforced by the core's `Knowledge_Read` and guest checks (SB-9 6.7), not by record sharing, so the API behaves the same in every calling context: trigger, batch, Queueable or `without sharing` caller code.
8. **The extension hook** (SB-9 section 5) runs exactly as it does for REST, because the API goes through the same resolver.

## 5. Access

- A subscriber user or integration user needs the `Knowledge_Reader` permission set, which carries the `Knowledge_Read` custom permission. Without it, every method throws `FORBIDDEN`. This is the same check as REST, done in the core.
- 10a adds Apex class access to `KnowledgeApi` in `Knowledge_Reader` for completeness. The platform does not enforce class access when one Apex class calls a `global` method, so the custom permission is the real gate, and the guide says so.
- Code in an automated context (Queueable, batch, scheduled job) runs as the user who started it. That user needs `Knowledge_Reader`.

## 6. Documentation (`packages/salesforce/docs/apex-api.md`)

This is the "documented" part of REQ-3. ApexDoc comments on `KnowledgeApi` carry the same text in short form. The guide covers:

1. The four signatures, the request fields with their defaults and ranges (from the OpenAPI document), and the result fields. It notes the Apex field renames (`maxItems`, `edgeType`, `edgeTypes`, `commitSha`, from SB-9 section 4).
2. One example per operation that uses only invented "Example Corp" node ids. Each example shows `try { ... } catch (<ns>.KnowledgeException e) { ... }` with a switch on `e.getCode()`.
3. The error table: code, when it happens, and whether it is retryable. It is copied from SB-7 4.3 and SB-9 6.8, with the `context.trigger` rule added if rule 5 applies.
4. The limits from rule 4, and the search index lag (SB-9 6.3).
5. The required permission set (section 5).
6. Stability: the `global` signatures follow the contract versioning (SB-7 section 7), and minor versions only add optional fields.

The guide has no org-specific values. `<ns>` stays a placeholder until Alex registers the namespace (SB-12 section 10).

## 7. Test approach

### 7.1 Unit tests (`KnowledgeApiTest`)

These run with `RunLocalTests` in a development scratch org, using SB-9's `KnowledgeTestData` with synthetic content. Coverage on `KnowledgeApi` is 100 %.

| # | Test | Proves |
|---|---|---|
| 1 | Each method with valid input against a committed fixture bundle | Same result fields as the SB-9 core test for the same input |
| 2 | Each method with `null` | `KnowledgeException`, `INVALID_REQUEST`, rule `required` |
| 3 | Each method with one invalid field (for example `maxItems = 0`, a bad node id pattern) | `KnowledgeException` carries the same `details` as the validator (SB-9 6.6), and `getHttpStatus() = 400` |
| 4 | Unknown node | `NODE_NOT_FOUND`, `isRetryable() = false` |
| 5 | A user without `Knowledge_Reader` (`System.runAs`) | `FORBIDDEN` from all four methods |
| 6 | A core seam that throws a `NullPointerException` | Wrapped as `INTERNAL`, `isRetryable() = true`, and the message contains no stack trace |
| 7 | Catchability: a test helper class that calls each method inside `try/catch (KnowledgeException e)` | The exception is caught by its declared type |
| 8 | Trigger context (only if rule 5 applies): a trigger on a test-only setup object, or a `@TestVisible` seam for `Trigger.isExecuting`, calls `searchNodes` | `INVALID_REQUEST`, rule `context.trigger`, before any SOSL query (`Limits.getSoslQueries() = 0`) |
| 9 | The caller changes the returned DTO and calls again | The second result is unaffected |

### 7.2 Parity tests (`KnowledgeApiParityTest`)

This is the REQ-3 acceptance check ("same result as the equivalent REST call"). For each operation it runs a table of inputs: a normal case, a boundary value, an empty result, each error code the operation can return, and one input with the hook configured. For each input it:

1. Calls `KnowledgeApi.<operation>(request)`. On success, it serialises the result with `KnowledgeRestSupport` (the SB-9 JSON writer). On error, it serialises the `KnowledgeException` as the error envelope plus the HTTP status.
2. Calls the matching REST resource with the same input in `RestContext` (the path, query or body built from the same request values), and takes the status and body.
3. Asserts that the statuses are equal and that the two bodies are deep-equal as parsed JSON.

Both calls read the same committed bundle in the same test, so the comparison is exact. Search uses the same `Test.setFixedSearchResults` for both calls. Because the serialiser is shared, this test checks behaviour parity (same core path, same validation, same errors, same hook). The SB-9 contract tests separately check the JSON shape.

### 7.3 Subscriber-org check (`expected-components.json`)

10a adds the following:

- `KnowledgeApiTest` and `KnowledgeApiParityTest` to `tests`. They then run in the installed subscriber org (SB-12 5.1 step 3).
- The SB-12 section 7 "Apex API (12b, from SB-10)" entry. `verify` runs this anonymous Apex in the installed org:

```apex
try {
    <ns>.KnowledgeRequests.GetNodeRequest r = new <ns>.KnowledgeRequests.GetNodeRequest();
    r.nodeId = 'verify-install-probe-0';
    <ns>.KnowledgeApi.getNode(r);
    System.assert(false, 'expected an exception');
} catch (<ns>.KnowledgeException e) {
    System.assert(e.getCode() == 'NODE_NOT_FOUND' || e.getCode() == 'FORBIDDEN', e.getCode());
}
```

It shows that the `global` API compiles from outside the namespace, that the exception can be caught across the namespace boundary, and that the error codes are the documented ones.
