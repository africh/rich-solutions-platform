## 1. Goal

Create the Salesforce DX project for the Rich Solutions base package, so that every later build story (SB-8 to SB-11) adds metadata to one place. Prove that the project can produce an unlocked 2GP package version that installs with no errors and no manual steps into a fresh scratch org and into a sandbox. Then, once SB-9 to SB-11 have landed, prove that the REST, Apex and Agentforce components are present after install.

Out of scope: promoting a version to released (Alex only, section 8), AppExchange listing or security review, managed packaging, client extension packages (outside this repo, ip-boundary section 3.2).

### 3.1 `sfdx-project.json`

```json
{
  "packageDirectories": [
    {
      "path": "force-app",
      "default": true,
      "package": "<Package Name>",
      "versionName": "MVP",
      "versionNumber": "0.1.0.NEXT",
      "versionDescription": "Rich Solutions knowledge service base package"
    }
  ],
  "namespace": "<ns>",
  "sfdcLoginUrl": "https://login.salesforce.com",
  "sourceApiVersion": "<latest GA API version in the Dev Hub at build time>",
  "packageAliases": {}
}
```

- `<Package Name>` and `<ns>` are Alex's choices (section 10). The namespace is public once installed, so committing it is fine. It must not name a client.
- `packageAliases` is filled by `sf package create` and `sf package version create`. The `0Ho` and `04t` ids are package identifiers, not secrets, and may be committed.
- **No `dependencies` key.** That is ip-boundary rule 3.1.1, and `package-check` enforces it (6.1).
- `sourceApiVersion`: the Developer pins the newest GA version at build time and records it in the PR. It changes only through a PR.

### 3.2 Layer folders

The four ADR-001 layers become four folders under `force-app/main/`, plus `admin/` for package-wide items. Salesforce ignores folder names when deploying, so this is purely for people and for `package-check`. Rule, checked by 6.1: Apex in a lower layer must not reference a class that lives in a higher layer (Contract, then Storage, then Service, then Exposure). `admin/` may reference any layer, and nothing references `admin/` except tests.

### 3.3 Placeholder content in 12a

A package version needs at least one component, and Apex needs 75 % coverage to be promoted later. Slice 12a ships:

- `KnowledgePackageInfo` (`global with sharing`): `global static String namespacePrefix()` returns the namespace from the class's own type name, and `global static String contractVersion()` returns the major.minor of the SB-7 services contract (`knowledge-services.openapi.yaml` `info.version`) the package implements. It is a constant, changed in the same PR that changes the contract: `'1.0'` in 12a, `'1.1'` once SB-8 slice 8b adds `BUNDLE_NOT_FOUND` (SB-8 7.2). It is a real, lasting API: support scripts and `verify-install` use it. There is deliberately no installed-version method: `System.requestVersion()` returns only the caller's major.minor binding, not the installed full version, and the installed version is already checked through `InstalledSubscriberPackage` (section 7).
- `KnowledgePackageInfoTest`: 100 % coverage.
- Permission set `Knowledge_Admin`: Apex class access to `KnowledgePackageInfo`. Later stories add their objects and classes to it. SB-8 adds `Knowledge_Sync`, and SB-9 adds a reader permission set.

### 3.4 Scratch definitions

- `project-scratch-def.json`: `edition: Developer`, no `features`, `settings` limited to `languageSettings` defaults. This is deliberately the plainest org shape. If the package installs and its tests pass here, it has no hidden feature dependency (ADR-001 C1, ip-boundary rule 3.1.3).
- `project-scratch-def.agentforce.json`: the same plus the features and settings Agentforce needs in a scratch org. The Developer takes the exact feature names from the current Salesforce scratch-org feature list during 12a and records the source in the README. It is used only for SB-11 testing, never as the install target for AC 3.

## 4. Package version creation

`scripts/create-version.sh`:

```
sf package version create --package "<Package Name>" --installation-key-bypass \
  --code-coverage --definition-file config/project-scratch-def.json --wait 60 --json
```

- `--code-coverage` always runs, so every version can later be promoted without a rebuild.
- `--installation-key-bypass` is used for development versions. Whether released versions need an installation key is Alex's decision (section 10).
- The script prints the `04t` id and the version number, and fails on any non-success status.
- The first time only: `sf package create --name "<Package Name>" --package-type Unlocked --path force-app` (namespace from `sfdx-project.json`). The Developer runs it once the Dev Hub exists and commits the resulting `packageAliases`.

## 5. Install

### 5.1 Scratch org (AC 3)

`scripts/install-and-test.sh <04t>`:

1. `sf org create scratch --definition-file config/project-scratch-def.json --no-namespace --duration-days 1 --alias pkg-install-<timestamp>`. `--no-namespace` is required: the project's `sfdx-project.json` sets `namespace`, and without the flag the CLI creates a scratch org with that namespace, into which the package cannot be installed. Development scratch orgs (`create-scratch.sh`) stay namespaced; only the install target uses the flag.
2. `sf package install --package <04t> --target-org <alias> --security-type AdminsOnly --no-prompt --publish-wait 10 --wait 30`. `--publish-wait` covers the delay after `version create` before a new version is available to install. A non-success status fails the script.
3. `sf apex run test --target-org <alias> --class-names <list> --code-coverage --wait 30`, where `<list>` is the `tests` array of `expected-components.json` with each class prefixed `<ns>.` (12a: `<ns>.KnowledgePackageInfoTest`). `RunLocalTests` is not used: it skips tests that come from installed packages, so in a fresh subscriber org it runs zero tests and passes trivially. The script also fails if the run reports zero tests executed, or fewer than the length of `<list>`; any test failure fails the script.
4. `scripts/verify-install.sh <alias>` (section 7). In 12a only the 12a entries of `expected-components.json` are checked.
5. `sf org delete scratch --target-org <alias> --no-prompt`, always (trap on exit).

"Zero manual steps" means steps 1 to 4 run unattended, end to end. REQ-12 (zero-manual-step install, Needs Alex) may raise this to cover Agentforce setup; see 5.3.

### 5.2 Post-install setup

The base package does not use an `InstallHandler` in the MVP. Install must have no side effects that can fail (ADR-001 C1). Optional setup goes in `scripts/post-install.sh`, which is idempotent and safe to re-run:

- Assign `Knowledge_Admin` to the running admin user.
- Schedule the SB-8 purge job (SB-8 section 8) if it is not scheduled yet.

Nothing in 5.1 depends on post-install. The package is "installed cleanly" without it; post-install only switches on optional behaviour.

### 5.3 Agentforce components

To keep install feature-independent, the package carries the Agentforce-facing **logic** as `@InvocableMethod` Apex classes in `exposure/` (SB-11). Invocable Apex installs in any org and shows up as an available Apex action for agents in orgs where Agentforce is on.

Agent-specific metadata (agent actions and topics, the `GenAi*` metadata types) goes in `unpackaged/agentforce/` and is deployed by `post-install.sh --agentforce` to orgs that have Agentforce. The reason: if that metadata is packaged, every subscriber org may need Agentforce enabled before the package installs, which breaks AC 3 in a plain scratch org.

The Developer checks this assumption in 12a. Add one `GenAiFunction` stub to a throwaway branch's package directory and try `sf package version create`, then try to install the result into the plain scratch shape. Record the outcome in the PR.

- If both succeed, the SB-11 spec may move agent metadata into the package. The TA updates this spec.
- If either fails, the split above stands.

For AC 5, "Agentforce components present" means: the invocable action classes are installed and marked invocable (verified as in section 7).

### 5.4 Sandbox (AC 4)

The steps are the same as 5.1 steps 2 to 4, against a sandbox that Alex provides and authorises (`sf org login web --alias pkg-sandbox` is run by Alex, or the Developer uses a JWT login Alex sets up). Agents must not create or buy a sandbox. The evidence is the command output, with the org id and instance URL removed. If no sandbox is available when 12b is otherwise done, the story waits in In PR with an Operator Inbox Blocker rather than skipping the AC.

## 6. Checks

### 6.1 `tools/package-check static` (no org needed; runs on every PR touching `packages/salesforce/`)

| # | Check | Source |
|---|---|---|
| S1 | `sfdx-project.json` parses; exactly one package directory; no `dependencies` key in any package directory | ip-boundary 3.1 rule 1 |
| S2 | `namespace` is set and is not a placeholder (`<ns>`), once 12a merges with Alex's value | ADR-001 decision 1 |
| S3 | No Apex, flow or metadata file references a namespaced name (`<prefix>__<Name>__c` and the other custom suffixes) whose prefix is not the package's own namespace | ip-boundary 3.1 rule 2 |
| S4 | Layer rule in 3.2: no reference from a lower layer folder to a class defined in a higher one | ADR-001 layers |
| S5 | Every Apex class has a test class, or is a test class | Coverage gate |
| S6 | No `SeeAllData=true` | Clean-org install |
| S7 | Public-repo scan over `packages/` and `tools/`: no 15/18-char org-id patterns starting `00D`, no `*.my.salesforce.com` hosts other than placeholders, no private keys (`-----BEGIN`), no `force://` auth URLs | SP-1 |
| S8 | `.forceignore` excludes local org state (`.sf/`, `.sfdx/`, `**/.localdevserver/`) | Hygiene |

Exit code non-zero on any failure, one line per finding as `path:line: Sx message`. Unit tests in `tools/package-check/tests/` include one failing fixture per check.

### 6.2 CI workflow `package-ci.yml`

- **Triggers:** `pull_request` and `push` to `main`, paths `packages/salesforce/**` and `tools/package-check/**`, plus `workflow_dispatch` (manual). It is path-filtered, so it must not be made a required check on `main` (QA note 2 on PR #9). The whole file waits on the Inbox decision in section 3.
- **Job `static`:** Python 3.12, `package-check static`, `package-check` unit tests. No secrets.
- **Job `scratch-install`:** runs only when the repository has the Dev Hub secret. Job-level `if` cannot read secrets, so a small `check-secrets` job outputs `has_devhub`, and this job uses `needs: check-secrets` with `if: needs.check-secrets.outputs.has_devhub == 'true'`. Steps: JWT login to the Dev Hub, `create-version.sh`, `install-and-test.sh <04t>` (which creates the install-target org with `--no-namespace`, 5.1). It never runs on pull requests from forks, and on `workflow_dispatch` it runs only when the dispatched ref is `main`. Secrets are set by Alex in this repository's settings (section 10). Version creation consumes the Dev Hub's daily version-creation allowance, so this job runs on `push` to `main` and on manual dispatch, not on every PR commit.

## 7. Install verification (`expected-components.json`, `package-check verify`)

`verify` reads the installed org through the CLI (`sf data query --use-tooling-api --json`) and checks each expected entry:

| Kind | Expected entries | How checked |
|---|---|---|
| Package | The package is in `InstalledSubscriberPackage` with the expected version | Tooling query |
| Apex API (12a) | `KnowledgePackageInfo` is installed in the namespace and `global` | `ApexClass` with `NamespacePrefix = '<ns>'`; anonymous Apex calling `<ns>.KnowledgePackageInfo.namespacePrefix()` returns `<ns>` and `contractVersion()` returns the expected value |
| Tests (12a onwards) | The `tests` array: every package test class to run in the subscriber org (5.1 step 3) | Each class is present with `NamespacePrefix = '<ns>'`; the test run in 5.1 executes all of them |
| Permission sets (12a) | `Knowledge_Admin` | `PermissionSet` query |
| REST (12b, from SB-8 and SB-9) | SB-8: the import resource `/knowledge/v1/bundles/*`. SB-9: the query resources `/nodes/*`, `/search`, `/context` | `ApexClass` bodies are hidden in the subscriber org, so the checks are live calls. Query: `GET /services/apexrest/<ns>/knowledge/v1/nodes/verify-install-probe-0` must return `404 NODE_NOT_FOUND` in the SB-7 error envelope, not a platform "Could not find a match for URL" error. The id matches the SB-7 node id pattern `^[a-z0-9][a-z0-9_/-]{0,254}$` and cannot exist in a fresh org, so a conformant SB-9 returns 404, not 400. Import: `GET /services/apexrest/<ns>/knowledge/v1/bundles/verify-install-probe@0000000000000000000000000000000000000000` (a valid `bundle.id` per SB-8 4.5, which no vault produces) must return the SB-7 error envelope with `404 BUNDLE_NOT_FOUND` (SB-8 section 7.2), or `403` if the verifying user lacks `Knowledge_Import`; either shows the resource is installed |
| Apex API (12b, from SB-10) | The global service entry point named in the SB-10 spec | Anonymous Apex compiles a call to it |
| Agentforce (12b, from SB-11) | Each invocable action class named in the SB-11 spec | Anonymous Apex lists them through `Invocable.Action.createCustomAction('apex', '<ns>__<Class>')` without error; a fallback check is the class's presence in the namespace |

SB-8 (slice 8b), SB-9, SB-10 and SB-11 each add their entries, including their test classes in `tests`, to `expected-components.json` in their own PRs, and their specs say so. `verify` fails on any missing entry and prints which.

## 8. Versioning and release

- Version numbers follow `major.minor.patch.build`. 0.x until the MVP demo. `minor` for new features. `patch` for fixes. A `global` member removed or changed in an incompatible way means `major` and follows the SB-7 versioning rules (ip-boundary 3.1 rule 4).
- Developers create beta (non-promoted) versions only. **Promoting a version to released is an Alex action** (`sf package version promote`), like merging. The agent PR records the `04t` it tested; Alex promotes that exact id.
- Every promoted version gets a git tag `pkg-v<major.minor.patch>` on the merged commit, created by Alex or by a later release story. Agents do not push tags.

## 9. Error handling

| Failure | Behaviour |
|---|---|
| `package-check static` finding | CI job fails with `path:line` findings; nothing else runs |
| Version create fails (coverage, compile, dependency) | Script exits non-zero and prints the Salesforce error list from `--json` |
| Install fails | Script exits non-zero, keeps the error, still deletes the scratch org |
| Package tests fail in the subscriber org | Script exits non-zero with failing test names |
| `verify` finds a missing component | Script exits non-zero, listing missing entries |
| Dev Hub limit reached (daily scratch orgs or versions) | Script exits non-zero with the limit message; the Developer reports it in the Handoff log; no retries in a loop |

Scripts never echo auth URLs, access tokens or org ids. They use `--json` output and print only the fields they need.
